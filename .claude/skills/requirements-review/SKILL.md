# 要件定義の計画を敵対的にレビューする

計画を書いた本人は、自分の読み方と調べた範囲を正しいと思っている。了承の前に、計画と依頼とリポジトリだけを渡した別のエージェントに壊しにいかせ、実装してから出る「思っていたのと違う」「Windows は？」「訳は？」「既存の要件とぶつかる」を今のうちに見つける。

レビュアーは [requirements-reviewer](../../agents/requirements-reviewer.md)（Opus、読むだけ）。

原則:

1. **レビュアーに結論を渡さない。** 渡すのは依頼の文面・計画・ユーザーとのやりとりだけ。「ここは確かめた」「ここが心配」のような自分の考えを書くと、レビュアーはそれに引きずられる。
2. **指摘をうのみにしない。** レビュアーの指摘も間違うことがある。自分でリポジトリを見て確かめてから仕分ける。
3. **退けた指摘も消さない。** 理由を付けて計画に残し、了承のときにユーザーが見られるようにする。

## 0. 使うとき・回し方

| 計画の大きさ（requirements スキルの 0 章） | レビュー |
| --- | --- |
| 小 | しない（requirements スキルを使わない大きさ） |
| 中 | レビュアー 1 つ（観点 1〜11 のすべて） |
| 大 | レビュアー 2 つを並べて走らせる。A: 観点 1〜3・10・11（目的・受け入れ条件・失敗時・範囲・ユーザーが決めること）、B: 観点 4〜9（既存の要件・Mac と Windows・17 言語・データと安全・手順の事実・確かめ方） |

レビューは計画 1 つにつき 1 回。仕分けのあとで要件の案が大きく変わった（要件が増えた・対象の OS が変わった・既存の要件を変えることになった）ときだけ、直した計画でもう 1 回まわす。3 回目はしない。

## 1. レビュアーに渡すものをそろえる

- **計画**: plan mode なら plan のファイルのパス。`docs/plans/<名前>.md` に書いたならそのパス。会話の中にしかなければ、本文をそのままプロンプトに入れる。
- **依頼の文面**: ユーザーの言葉をそのまま（要約しない）と、依頼の日付。
- **ユーザーとのやりとり**: requirements スキルの 4 章で聞いた質問と答え（そのまま）。

## 2. レビュアーを走らせる

Agent ツールで `subagent_type: "requirements-reviewer"` を呼ぶ（エージェントの定義で `model: opus`）。大のときは A と B を 1 つのメッセージで並べて呼ぶ。

プロンプトの形:

```text
次の要件定義の計画を、了承の前に敵対的にレビューしてください。
エージェントの定義（.claude/agents/requirements-reviewer.md）の観点と形で返してください。
<大のときだけ> 今回は観点 <番号> だけを見てください。ほかの観点は、別のレビュアーが見ています。

## 依頼（YYYY-MM-DD）
<ユーザーの言葉そのまま>

## ユーザーとのやりとり
<質問と答えそのまま。なければ「なし」>

## 計画
<ファイルのパス、または本文>
```

自分の推測・心配・「ここは確かめ済み」は書かない（原則 1）。

## 3. 指摘を確かめて仕分ける

指摘ごとに、根拠（ファイルと行・spec の ID・コマンド）を自分で見て確かめ、次の 3 つに分ける。

| 仕分け | どんなとき | すること |
| --- | --- | --- |
| **直す** | 指摘が正しく、計画を直せば済む（requirements スキルの 3 章の (a)・(b)） | 計画を直す |
| **聞く** | 指摘が正しく、ユーザーにしか決められない（3 章の (c)） | 4 でユーザーに聞く |
| **退ける** | 根拠が誤り・もう計画に書いてある・依頼の範囲の外・効果に見合わない | 退ける理由を書く |

- 重さは、確かめたうえで付け直してよい（レビュアーの「致命」が本当は「軽微」なこともある）。
- 「推測」とされた指摘は、確かめられたら直す・聞くに、確かめられなければ「仮に決めたこと」に足す。
- 「見られなかったこと」に挙がった観点は、自分で見るか、見られなかったことを計画に書く。
- 並べた 2 つのレビュアーが同じことを言っていたら、1 つにまとめる。

## 4. 計画を直し、必要ならユーザーに聞く

- 「直す」の指摘を計画に入れる（要件の案・受け入れ条件・失敗時・設計判断の案・やらないこと・手順・確かめ方）。
- 「聞く」があれば、requirements スキルの 4 章の決まりで、AskUserQuestion でまとめて聞く（推奨を先頭に、調べた事実を一言添える）。requirements スキルの「質問は多くても 2 回」の 2 回目に当たる。まだ 2 回目が残っていなければ、推奨で決めて「仮に決めたこと」に書き、了承のときに見てもらう。
- 要件の案が大きく変わったら、0 章のとおりもう 1 回だけレビューする。

## 5. 計画に「敵対的レビュー」の節を足す

計画の最後（「仮に決めたこと」の前）に、次の節を足す。了承のときにユーザーが、何が見つかって何が直ったかを見られるようにする。

```markdown
## 敵対的レビュー
YYYY-MM-DD、requirements-reviewer（Opus）<1 つ / 2 つ並べて>、<1 / 2> 回。

| # | 重さ | 指摘 | 仕分け | どうしたか |
| --- | --- | --- | --- | --- |
| 1 | 重大 | Windows 版の同じ設定に触れていない | 直す | 手順 3 に Windows を足した |
| 2 | 重大 | 失敗時に HUD に何を出すかが決まっていない | 聞く | ユーザーの答え「…」を受け入れ条件に入れた |
| 3 | 軽微 | REQ-DIC-0xx とぶつかる | 退ける | REQ-DIC-0xx は辞書の登録の話で、この計画は触らない |

見られなかったこと: なし
```

## 6. requirements スキルに戻る

requirements スキルの 7 章（了承を取る）に進む。了承を求めるときの一言に、レビューで直したこと・聞いたこと・退けたことの数を添える（例: 「敵対的レビューで重大 2・軽微 3。2 つ直し、1 つは上でお聞きし、2 つは理由を書いて退けました」）。
