# 依頼から要件と計画を固める

このリポジトリでは、要件（REQ）を変えるにはユーザーの合意が要り、spec を先に書き、コードにタグを付け、UI の文字列とプロンプトは 17 言語をそろえ、Mac と Windows の両方を考える（[CLAUDE.md](../../../CLAUDE.md)、[docs/README.md](../../../docs/README.md)）。依頼の言葉だけで作り始めると、あとで「思っていたのと違う」「Windows は？」「訳は？」「既存の要件とぶつかる」が出て、作り直しになる。そこで、作る前に要件と計画をユーザーと合意する。

原則:

1. **合意するまで、spec とコードを書き換えない。** 読む・調べる・手元で試すのはよい。
2. **聞くのは、ユーザーにしか決められないことだけ。** コード・spec・決まりで分かることは調べて決め、計画に「こう決めた」と書く。
3. **質問はまとめて 1 回（多くても 2 回）。** 各質問に推奨を付ける。
4. **計画は、ほかのエージェントがそれだけを読んで実装できるくらい具体的に書く。** 触るファイル・型・関数、足す ID、確かめるコマンドまで。

## 0. 大きさを見る

| 大きさ | 例 | やること |
| --- | --- | --- |
| 小 | 誤字、振る舞いを変えない整理、要件どおりに戻すだけのバグの直し | このスキルは使わない。タグと spec を確かめて直す |
| 中 | 既存の機能の振る舞いを変える、設定を 1 つ足す、片方の OS だけの小さな機能 | 1〜7 を短く。計画は会話の中（plan mode なら plan のファイル） |
| 大 | 新しい機能、複数の領域、Mac と Windows の両方、外部のサービス・費用 | 1〜7 をすべて。調べたことが多ければ [docs/plans/](../../../docs/plans/) に `<名前>.md` で書き、[docs/roadmap.md](../../../docs/roadmap.md) から参照する |

バグの直しでも、要件がその振る舞いを決めていない・要件の書き方があいまい・直すと別の要件とぶつかるときは「中」として扱う。

## 1. 依頼を読み解く

依頼の文面を次の 3 つに分けて書き出す。

- **目的**: 何に困っていて、何をしたいのか（言われた手段ではなく、その先にあるもの）。
- **観察できる結果**: 何が起きれば「できた」と言えるか。受け入れ条件の元になる。
- **前提**: 依頼が当然と思っていること（どの OS か、どの画面か、既定で有効か、など）。

依頼の日付（今日の日付）と要旨を控える。要件の「出典」に書く。

## 2. 今の作りと決まりを調べる

- **spec**: 関係する領域（DIC・MTG・COM・REL）の [docs/spec/](../../../docs/spec/) で、同じことをしている要件、ぶつかる要件、「食い違い（ユーザーの確認待ち）」を探す。
  ```bash
  grep -n "^### " docs/spec/dictation.md          # 項目の一覧
  grep -rn "<キーワード>" docs/spec/               # 言葉で探す
  ```
- **コード**: 変える場所の `// 要件:`・`// 設計判断:` のタグを読み、その ID の spec を読む。タグのないところは暗黙の振る舞い（変えるなら格上げするかを計画に書く）。`.codegraph/` があれば CodeGraph で探す。
- **roadmap と計画**: [docs/roadmap.md](../../../docs/roadmap.md) と [docs/plans/](../../../docs/plans/) に同じ `FUT-…` がないか。あれば、それを実装する計画にする（spec に移し、roadmap には「→ REQ-…」だけを残す）。
- **design**: [docs/design/](../../../docs/design/) で今の構成とデータの流れを見る。保存するもの・外に送るものに関わるなら [design/security.md](../../../docs/design/security.md) も。
- **Windows**: [windows/README.md](../../../windows/README.md) で Mac 版との差を見る。同じ機能が Windows にあるか、作れるか。
- **確かめ方の材料**: 今ある自己テストの CLI（入口は `Sources/Hanasu/main.swift`、中身は `Sources/Hanasu/*CLI.swift`）、`windows/Hanasu.Core.Tests` のテスト。

調べる範囲が広ければ Explore エージェントに任せ、結論（関係する ID・ファイル・型と関数の名前）だけを受け取る。

## 3. 決まっていないことを洗い出す

次の観点で、決まっていないことを並べる。

| 観点 | 見ること |
| --- | --- |
| 目的と範囲 | 何をやって、何をやらないか。やらないことのうち、あとでやるもの |
| 対象 | Mac / Windows / 両方。片方だけなら、もう片方は対象外か、あとでやるか（FUT） |
| 入口 | ショートカット・メニュー・設定の項目・HUD・CLI。既定で有効か、オフにできるか |
| 振る舞いの細部 | 既定値・上限・順番・タイミング・どこに出すか |
| うまくいかないとき | ネットがない、認証が切れた、権限がない、AI が失敗した・遅い、途中でやめた、入力が空・長すぎる |
| 既存の要件 | 変える・ぶつかる・広げる REQ。変えるならユーザーの合意が要る |
| 文字列とプロンプト | 足す・変える UI の文字列と AI への指示（17 言語の訳が要る。[i18n スキル](../i18n/SKILL.md)）。README に書くか（書くなら 15 の訳も） |
| データと安全 | 保存するもの・場所・期間、外に送るもの、鍵や認証の扱い |
| 確かめ方 | 自己テストの CLI・テスト・実機のどれで確かめるか。足す CLI・テストはあるか |

並べたものを、3 つに分ける。

- **(a) 調べれば分かる**（コード・spec・決まりにある）→ 調べて決め、計画に書く。
- **(b) 実装する人が決めてよい細部**（既定値・区切り方・内部の作り）→ 設計判断の案として、推奨と理由を計画に書く。迷ったらこちら。
- **(c) ユーザーにしか決められない**（目的・範囲・優先・対象の OS・既存の要件を変える・外部のサービスの費用・ユーザーに見える振る舞いのうち好みで分かれるもの）→ 4 で聞く。

## 4. ユーザーに聞く

- (c) だけを、AskUserQuestion で 1 回にまとめて聞く（1 回に 4 問まで）。
- 各質問は、それだけを読んで分かるように書く。調べて分かった事実を一言添える（例: 「今は REQ-… で『…』と決まっています。依頼のとおりにすると、この要件を変えることになります。変えますか？」）。
- 選択肢は 2〜4 つ。推奨を先頭に置き、ラベルの最後に「（推奨）」と付ける。各選択肢に、選んだら何が変わるかを書く。
- 依頼の言葉と既存の要件がぶつかるときは、どちらに合わせるかを聞く。勝手に要件を書き換えない。
- 答えから新しい (c) が出たら、もう 1 回だけ聞く。それでも残るものは推奨で決め、計画の「仮に決めたこと」に書く（了承のときに見てもらう）。
- (a)・(b) は聞かない。計画に書いて、7 でまとめて了承をもらう。

## 5. 計画を書く

次の形で書く。中なら会話の中か plan のファイルに、大なら `docs/plans/<名前>.md` にも置く（計画の状態は「計画（未実装）」。実装したら spec に移し、plans には結果へのリンクを残す）。

```markdown
# <機能の名前>

## 目的
YYYY-MM-DD の依頼「<要旨>」。<何に困っていて、何ができるようになるか>

## 要件の案
### REQ-<領域>-<番号> <短い名前>（新規）
- 内容: 何をするか
- 受け入れ条件: 外から観察できる振る舞い（うまくいかないときも）
- 出典: YYYY-MM-DD の依頼「…」（了承の日付を足す）
- 対象: Mac / Windows
- 実装の場所: 型・関数の名前（予定）
- 確かめ方: CLI のコマンドやテスト。なければ「実機で確かめる」

### 変える要件（ユーザーの合意が要る）
- REQ-…: 今「…」 → 「…」。理由: …

## 設計判断の案
### DEC-<領域>-<番号> <短い名前>
- 決めたこと: …
- 理由: …
- 関係する要件: REQ-…
- 対象: Mac / Windows

## やらないこと
- …（あとでやるなら roadmap に FUT-<番号> として足す）

## 手順
1. spec に要件・設計判断を書く（docs/spec/<領域>.md。roadmap から移すなら roadmap も）
2. Mac: <ファイル・型・関数> を … する。タグを付ける
3. Windows: <ファイル・型・関数> を … する（対象外なら書かない）
4. UI の文字列・プロンプトを 17 言語で入れる（i18n スキル。i18n エージェントに言語を分けて任せる）
5. design/ を直す。README を直すなら 15 の訳も
6. 確かめる（下）

## 確かめ方
- `swift build`
- `python3 scripts/check-spec.py`、`python3 scripts/check-i18n.py`
- `.build/debug/Hanasu --<自己テストの CLI>`（足すなら `// 確かめ方: REQ-…` を付ける）
- `cd windows && dotnet test Hanasu.Core.Tests`
- 実機で見ること: …

## 敵対的レビュー
（6 で requirements-review スキルが足す）

## 仮に決めたこと
- …（推奨で決めたもの。了承のときに見てもらう）
```

書き方:

- 要件は「何をするか」（外から見える振る舞い）、設計判断は「どうやるか」と要件が決めていない細部（[docs/README.md](../../../docs/README.md) の 2 章）。
- 番号は、その領域の同じまとまり（10 刻み）の続きの空き番号を使い、使い回さない（廃止した番号も使わない）。ほかの PR が同じ番号を使っていることがあるので、spec に書くときに確かめ直す。
  ```bash
  grep -ho "REQ-DIC-[0-9]*" docs/spec/*.md | sort -u | tail -5
  git fetch origin && gh pr list --state open --json number,title,headRefName
  ```
- 受け入れ条件は、確かめ方で本当に確かめられる形にする（「自然に」「速く」ではなく、何が・どこに・どのくらいで）。
- 手順は、触るファイルと型・関数の名前まで書く。独立して進められる手順（同じファイルを触らず、ほかの手順の結果を待たないもの）は、そう分かるように書く。

## 6. 敵対的レビューを受ける

計画が書き上がったら、了承を求める前に [requirements-review スキル](../requirements-review/SKILL.md) の手順で、[requirements-reviewer エージェント](../../agents/requirements-reviewer.md)（Opus）に計画を敵対的にレビューさせる。指摘を自分で確かめて「直す・聞く・退ける」に仕分け、計画を直し、計画に「敵対的レビュー」の節を足す。レビューで新しく (c) が出たら、4 の 2 回目として聞く。

## 7. 了承を取る

- plan mode の中なら、計画を ExitPlanMode で出す。plan mode でなければ、計画を見せて「この計画で進めてよいか」を聞き、答えを待つ。「変える要件」「敵対的レビュー」「仮に決めたこと」は、見落とされないように計画の中で目立たせる。
- 直しを頼まれたら、計画を直してもう一度見せる。
- 了承をもらったら、その日付を要件の「出典」に書き（例: 「2026-11-08 の依頼『…』、同日に計画を了承」）、PR の本文の「新しい要件・要件の変更」にも書く。
- 了承のあとで、計画から外れる必要が出たら:
  - 要件（ユーザーに見える振る舞い・範囲・対象）に関わるなら、止めてユーザーに聞く。
  - 設計判断の範囲なら、決めて spec に理由を書き、終わったときの報告で伝える。

## 8. 実装に入る

- 手順の最初は、spec に要件と設計判断を書くこと。そのあとは [docs/README.md](../../../docs/README.md) の 6 章（変更の手順）と、[i18n](../i18n/SKILL.md)・[pr-merge](../pr-merge/SKILL.md) のスキルに従う。
- 計画を、実装のあいだの道しるべにする。手順を終えるたびに計画と照らし、受け入れ条件をすべて確かめてから終える。確かめられなかった条件は、終わったときの報告に書く。
