# Hanasu 会議記録 — 要件定義・仕様・技術選定

Google Meet・Slack ハドル・Microsoft Teams などのオンライン会議の音声を Mac 上で拾い、
話者ごとに分けた文字起こしと議事録を残す機能。既存の音声入力アプリ Hanasu に機能として追加する。

- 対象 OS: macOS 26 (Tahoe) 以降 / Apple Silicon
- 作成日: 2026-11-02

---

## 1. 背景と目的

- オンライン会議の内容を、あとから検索・共有できる形で残したい。
- 会議ツールが Meet / Slack / Teams とばらばらなので、ツールごとの録画・文字起こし機能に頼らず、1 つの方法でまとめて記録したい。
- 「誰が何を言ったか」が分かる形（話者分離）にしたい。

## 2. 事例調査

### 2.1 2 つの方式

会議の記録ツールは、音声の取り方で 2 つに分かれる。

| 方式 | 仕組み | 主な製品 | 長所 | 短所 |
| --- | --- | --- | --- | --- |
| **A. 会議ボット** | 録音用のボットが参加者として会議に入る | Otter（OtterPilot）、Fireflies、tl;dv、[Recall.ai Meeting Bot API](https://recall.ai/product/meeting-recording-api) | 参加者ごとの音声ストリームが取れることがあり、話者分離が正確。録音中であることが全員に見える | 会議ツールごとに API・審査・サーバーが必要。Slack ハドルはボット用の公開 API がなく、Recall.ai のような専業ベンダーに頼ることになる。ボットが入ることを嫌がる相手もいる |
| **B. 端末で録音（ボットなし）** | 自分の Mac のマイクと、Mac が再生している音（システム音声）を録る | [Granola](https://docs.granola.ai/article/transcription)、Hyprnote（現 anarlog）、[Meetily](https://luci.memories.ai/alternatives/meetily)、[Recall.ai Desktop Recording SDK](https://www.recall.ai/product/desktop-recording-sdk) | 会議ツールを問わない（Meet・Slack ハドル・Teams・Zoom・対面も同じ方法）。サーバー不要。会議にボットが入らない | 相手側の音声は 1 本にまとまるので、相手が複数いると話者分離に別の処理が要る。録音していることを自分で伝える必要がある |

Granola のドキュメントでは「マイクを 1 チャンネル、PC で鳴っている音をもう 1 チャンネル」として録り、
自分の発言と相手側の発言を分けている。アプリ単位で切り分けず、システム全体の音をまとめて録る。

### 2.2 採用: B（端末で録音）

- Slack ハドルにはボットで参加する公開 API がない。Meet・Teams もボット運用にはクラウド基盤と審査が要り、個人で作るには重い。
- 端末で録れば、3 つのツールすべてに同じ仕組みで対応できる。既存の Hanasu の権限・署名・Gemini 設定もそのまま使える。
- 話者分離の弱点は、「マイク = 自分」と「システム音声 = 相手側」の 2 チャンネルに分けたうえで、相手側だけを話者分離モデルにかけて補う（後述）。

## 3. 要件定義

### 3.1 機能要件

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F1 | メニューバーとショートカットで会議の記録を開始・停止できる | 必須 |
| F2 | マイク（自分）とシステム音声（相手側）を別々に録音する | 必須 |
| F3 | 録音中、文字起こしをリアルタイムに表示する（自分／相手の区別つき） | 必須 |
| F4 | 終了後、相手側の音声を話者分離し、「話者1」「話者2」…に分ける | 必須 |
| F5 | 話者ごとの発言をまとめた文字起こし（時刻つき）を保存する | 必須 |
| F6 | Gemini で議事録（要約・決定事項・TODO）を作る | 必須 |
| F7 | 記録した会議を一覧し、文字起こし・議事録を読める・コピーできる | 必須 |
| F8 | 話者名を後から付け替えられる（「話者1」→「田中さん」） | あると良い |
| F9 | 会議アプリがマイクを使い始めたら「記録しますか？」と知らせる | あると良い（フェーズ 2） |
| F10 | 音声ファイルを残すか、処理後に消すかを選べる | あると良い |

### 3.2 非機能要件

| 項目 | 要件 |
| --- | --- |
| 対応ツール | Google Meet（ブラウザ）・Slack ハドル・Microsoft Teams。仕組み上、Zoom など Mac で音が鳴るものは全部対象 |
| 会議の長さ | 2 時間まで実用に耐えること |
| 処理時間 | 1 時間の会議で、停止から議事録完成まで数分以内 |
| プライバシー | 音声認識と話者分離は Mac 上で行う。外部（Gemini）に送るのは文字起こしテキストだけ |
| 負荷 | 会議中に CPU を使いすぎて会議ツールの音声が途切れないこと |
| 保存先 | `~/Documents/Hanasu/Meetings/` の下に、会議ごとに 1 フォルダ。Markdown なので他のツールでも読める |

### 3.3 対象外（今回はやらない）

- 会議ツールの画面・映像の記録
- 会議ツールへのボット参加
- 参加者の名前の自動取得（会議ツールの参加者一覧は読まない）
- 複数台の Mac の録音の統合

### 3.4 運用上の注意

- 録音は相手の同意を得てから行う。アプリは録音中であることをメニューバーに常に表示する。
- 社内規程で会議の録音・外部 AI の利用が制限されている場合はそれに従う。

## 4. 技術選定

### 4.1 システム音声の取得: Core Audio Process Tap

| 方式 | 判定 |
| --- | --- |
| 仮想オーディオデバイス（BlackHole 等）に出力を回す | ✕ ドライバーのインストールと出力先の切り替えが要る。会議中に自分が音を聞けなくなる設定ミスが起きやすい |
| ScreenCaptureKit の音声キャプチャ | △ 動くが「画面収録」権限が要り、ユーザーに画面まで録られるように見える |
| **Core Audio Process Tap**（`AudioHardwareCreateProcessTap`、macOS 14.2+） | ◎ 採用。ドライバー不要。「システムオーディオ録音」の権限だけで、Mac が再生している音を横取りせずに複製して受け取れる |

実装の流れ:

1. `CATapDescription(stereoGlobalTapButExcludeProcesses: [自分のプロセス])` で、自分以外が鳴らす音全体のタップを作る（Granola と同じく、アプリを限定しない）。
   - 設定で「会議アプリだけ」にすると、`kAudioHardwarePropertyProcessObjectList` から Chrome・Safari・Slack・Teams などの音声プロセスを探して `stereoMixdownOfProcesses` で限定する（フェーズ 2）。
2. `AudioHardwareCreateProcessTap` → タップを含む非公開の集約デバイスを `AudioHardwareCreateAggregateDevice` で作る。
3. `AudioDeviceCreateIOProcIDWithBlock` で音声バッファを受け取る。形式は `kAudioTapPropertyFormat` で取得。
4. Info.plist に `NSAudioCaptureUsageDescription`。初回に「システムオーディオ録音」の許可ダイアログが出る。

### 4.2 マイク

`AVAudioEngine` の入力ノード（音声入力機能と同じ）。

### 4.3 文字起こし: SpeechAnalyzer + SpeechTranscriber（チャンネルごと）

- 音声入力機能の検証で、`SpeechTranscriber` の方が発話を落とさなかったので、こちらを使う。
- マイク用とシステム音声用に 2 つの `SpeechAnalyzer` を並べて動かす。
- `attributeOptions: [.audioTimeRange]` を付けると、結果テキストの**語ごと**に時刻が付く。これを後で話者分離の結果と突き合わせて、語単位で話者を割り当てる（1 つの認識結果に複数の話者が混ざっていても分けられる）。
- 2 つのチャンネルの時刻は、録音開始時刻を 0 秒とした共通の時間軸にそろえる（`AnalyzerInput(buffer:bufferStartTime:)` に、そのチャンネルの開始のずれ＋累積サンプル数から計算した時刻を渡す）。

### 4.4 話者分離

相手側（システム音声）の録音ファイルに対して、会議終了後にまとめて実行する。
（マイク側は「自分」なので分離しない）

| 候補 | 仕組み | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. [FluidAudio](https://github.com/FluidInference/FluidAudio)（推奨）** | pyannote（speaker-diarization-community-1）を CoreML 化したもの。Apple Neural Engine で動く Swift パッケージ（Apache-2.0） | 音声を Mac の外に出さない。言語に依存しない。会議全体を 1 回で処理するので、話者番号が最後まで一貫する。公開値で DER 約 15%、実時間の 100 倍超の速さ | 外部パッケージの追加と、初回のモデルダウンロード（Hugging Face）が必要 |
| B. [Gemini 3.5 Transcribe](https://ai.google.dev/gemini-api/docs/transcribe.md.txt) の話者分離 | 音声ファイルを送ると、語ごとに `spk_1` などの話者と時刻が返る | 追加パッケージ不要 | 話者分離を使うと **1 回 30 分まで**、話者は 8 人まで（3 人以上は実験的）。長い会議は分割が要り、分割ごとに話者番号がずれる。音声を外部に送る。Vertex AI ではファイルを Cloud Storage に置く必要がある |
| C. 汎用 Gemini に音声を渡して「話者ごとに書き起こして」と頼む | プロンプトで指示 | 手軽 | 時刻や話者の一貫性が保証されない |

**採用: A（FluidAudio）**。利用者の承認を得て組み込んだ（2026-11-02）。

- バージョンは `0.17.7` に固定（2026-10-08 公開。公開直後の版は避けた）。
- `traits: []` を指定し、話者分離に不要なテキスト正規化のビルド済みバイナリ（NemoTextProcessing.xcframework, 87MB）をリンクしない。
- モデル（pyannote speaker-diarization-community-1 の CoreML 版）は初回の話者分離時に Hugging Face からダウンロードされ、以後はキャッシュを使う。
- 話者分離は差し替え可能な部品（`SpeakerDiarizer` プロトコル）にしてあり、失敗したときは「相手」1 人として扱って処理を続ける。

### 4.4.1 マイク側の話者分離（会議室など）

会議室から数人で参加し、1 つのマイクを共有する場合に備えて、設定「マイク側も話者を分ける」（初期値オフ）を用意した。

- オンにすると、マイクの録音（me.m4a）にも同じ話者分離をかける。
- マイク側で**話した時間がいちばん長い人を「自分」**、ほかを登場順に「同席者1」「同席者2」…（話者キー `room1`, `room2`）にする。
- 1 人で参加するときは、自分の声が 2 人に分かれる誤判定を避けるためオフのままにする。
- 議事録のプロンプトにも「同席者＝本人と同じ部屋で同じマイクを使う参加者」と説明を加えた。

合成音声での確認（マイク側に Flo と Kyoko、相手側に Kyoko と Eddy）では、マイク側の 2 人が「自分」と「同席者1」に正しく分かれた。
ただし、同じ音声合成エンジン（Eloquence）の声どうし（Flo と Grandpa）は 1 人にまとめられた。声の特徴が近すぎるためで、実際の人の声ではここまで似ることは少ない。

### 4.5 話者の割り当て

1. FluidAudio の結果 `[(speakerId, 開始秒, 終了秒)]` と、相手側の語ごとの時刻を突き合わせ、語の時刻を含む区間の話者を割り当てる。
   - 語の時刻は「語の終わり寄り 0.4 秒」の中央を使う（無音のあとの最初の語には無音の分まで長い時間が付くため）。
   - 区間と区間のすき間にある語は、前の区間の終わりから 0.3 秒以上あいて始まっていれば次の話者、そうでなければ前の話者にする（話者分離は話し始めの検出が 1 秒前後遅れることがあるため）。
2. 同じ話者が続く語をまとめて 1 発言にする。
3. マイク側の発言（話者 =「自分」）と時刻順に並べる。
4. 話者番号は登場順に「話者1」「話者2」…と付け直す。

### 4.6 スピーカーからの回り込み対策

イヤホンを使わないと、相手の声がスピーカーから出てマイクにも入り、「自分」の発言として二重に記録される。

- 推奨はイヤホン（設定画面とドキュメントで案内）。
- 後処理で、相手側に同じ時間帯・ほぼ同じ文字列の発言がある「自分」の発言を取り除く（時刻が重なり、文字の一致率が高いものを削除）。

### 4.7 議事録: Gemini（既存の認証設定を流用）

- 音声入力機能と同じ `GeminiClient`（API キー／サービスアカウント）を使う。
- 長い会議でも入る（1 時間の文字起こしは数万文字。Gemini の入力上限に十分収まる）。
- モデルは要約の質を優先して `gemini-3.8-flash` を初期値にする（音声入力と違って待ち時間が問題になりにくい）。
- 出力: 概要／話題ごとの要点／決定事項／TODO（担当・期限が分かれば）／話者名の推定（「話者1 は文中で『田中さん』と呼ばれている」など。推定であることを明記し、自動では書き換えない）。

### 4.8 議事録の型（テンプレート）

Granola のテンプレート（1on1・商談・採用面接など）にならい、会議の種類に合わせて議事録の見出しを変えられるようにした（`MinutesTemplate.swift`）。

| 型 | 見出しの構成 | 指示のねらい |
| --- | --- | --- |
| 自動（初期値） | 概要／話し合った内容（話題ごと）／決定事項 | 従来の議事録と同じ |
| 定例 | 概要／進捗（テーマごと）／報告・共有事項／課題・リスク／決定事項／次回までに確認すること | 会議に出ていない人が読んでも状況が分かる |
| 1on1 | 概要／近況・コンディション／話題と相談事／フィードバック／キャリア・成長／合意したこと／次回話したいこと | 本人の意図が伝わるように。個人的な事情は穏当な言い方で |
| 商談 | 概要／顧客の課題／提案内容／顧客の反応／懸念・質問／予算・時期・決裁 | 営業の記録としてそのまま使える。予算・時期・決裁者は必ず残す |
| ブレスト | 概要／出たアイデア（テーマごと）／有望なアイデア／論点・未解決の問い | アイデアはなるべく漏らさず、誰の案かを添える |
| カスタム | ユーザーが書いた指示に従う | 指示は `<user_template>` で囲んでシステム指示に入れる |

- どの型でも、最後に「アクションアイテム」（商談は「次のアクション」、ブレストは「次のステップ」）と「話者についてのメモ」の見出しを付ける。
- 選べる場面は 2 つ。
  - **記録を始める前**: 会議ノートの左下（録音する機器の下）の「議事録の型」。記録の開始時に会議へ記録する（`meeting.json` の `minutesTemplate` / `customMinutesPrompt`）。記録中は変えられない。
  - **あとから**: 会議ノートの「型: 〇〇」メニューで型を選び直すと、確認のあと議事録を作り直す。失敗したときは型も議事録も元のまま。
- 選んだ型とカスタムの指示は UserDefaults（`meetingMinutesTemplate` / `meetingCustomMinutesPrompt`）に置く。設定画面には出さず、会議ノートだけで選ぶ。

#### アクションアイテムの取り出し

あとで書き出しやリマインダーに使うため、アクションアイテムは Markdown とは別に構造化して受け取る。

1. 議事録の「## アクションアイテム」の本文には目印 `{{ACTION_ITEMS}}` だけを書かせる。
2. Markdown のあとに `<action_items>` で囲んだ JSON 配列（`owner`・`task`・`due`（YYYY-MM-DD）・`due_note`（「来週中」などの言い方））を出させる。期限は会議の日時を基準に日付に直せるときだけ `due` に入れる。
3. アプリが JSON を読み取り、目印を `- [ ] 内容（担当: 〇〇 / 期限: 11/6 (金)）` の一覧に置き換える。構造化した一覧は `meeting.json` の `actionItems` に保存する。
4. JSON が壊れていたときは、議事録のチェックボックスの行から読み取る。この機能より前に作った議事録（「## TODO」の行）も同じ方法で読み取るので、古い会議もリマインダーに登録できる。

Gemini の JSON モード（`responseSchema`）は使わず、テキストの応答の末尾に JSON を付けさせた。議事録の Markdown と一緒に 1 回で受け取れ、他の機能と共有している `GeminiClient` を変えずに済むため。

### 4.9 書き出し

tl;dv や Fireflies の書き出し（Slack・タスク管理）にならい、会議ノートの「書き出し」メニューから次を行える（`MeetingExport.swift`・`ReminderExport.swift`）。

| 項目 | 内容 |
| --- | --- |
| Markdown でコピー | 表示中のタブ（議事録か文字起こし）の Markdown |
| Markdown ファイルとして保存… / テキストファイルとして保存… | 表示中のタブを .md か .txt で保存。.txt は見出しを【】、箇条書きを「・」、チェックボックスを「□」にし、太字などの記号を外す |
| Slack 向けにコピー | 議事録を Slack の mrkdwn に直す。タイトルと日時を先頭に置き、「話者についてのメモ」（推測の内部メモ）は除く。見出し → `*太字*`、箇条書き → `•`、チェックボックス → `☐`、リンク → `<url\|text>`。太字は前後が空白でないと効かないので、日本語の文中では前後に空白を入れる。貼り付けて送る前提なので `&` `<` `>` のエスケープはしない |
| アクションアイテムをリマインダーに登録… | 選んだものだけを EventKit でリマインダーに登録する |

リマインダーへの登録:

- 一覧の初期の選択は、まだ登録していない「自分」の担当か担当が決まっていないもの。ほかの人の担当は外しておく（自分で選べば登録できる）。
- タイトルはやること、メモに担当・期限の言い方・会議名と日時を書く。`due` があれば日付だけの期限（終日）を付ける。
- 登録したアイテムには `reminderID` を保存し、「登録済み」と表示して二重登録を避ける。
- 権限（リマインダーのフルアクセス）は、シートの「登録」を押したときに初めて求める。Info.plist に `NSRemindersFullAccessUsageDescription`、Hardened Runtime 用に `com.apple.security.personal-information.calendars` の entitlement を足した。許可済みなら登録先のリストを選べる。

## 5. アーキテクチャ

```
                         ┌───────────────────────── MeetingRecorder（司令塔）──────────────────────────┐
                         │                                                                             │
 マイク ── AVAudioEngine ─┼─▶ ChannelTranscriber「自分」 ── SpeechAnalyzer ──▶ 語＋時刻 ─┐              │
                         │        └─ AVAudioFile（me.m4a）                               │              │
                         │                                                               ├─▶ ライブ表示  │
 システム音声 ─ Process Tap┼─▶ ChannelTranscriber「相手」 ── SpeechAnalyzer ──▶ 語＋時刻 ─┘              │
 （集約デバイス＋IOProc）  │        └─ AVAudioFile（others.m4a）                                          │
                         └──────────────────────────────┬──────────────────────────────────────────────┘
                                                        │ 停止
                                                        ▼
                    後処理: 確定 → 話者分離（others.m4a）→ 話者割り当て → 回り込み除去 → 並べ替え
                                                        │
                                                        ▼
                                Gemini で議事録 → 保存（transcript.md / minutes.md / meeting.json）
```

### 5.1 状態遷移

```
idle ──開始──▶ starting ──（権限OK・タップ作成・認識開始）──▶ recording
recording ──停止──▶ finishing（認識の確定）──▶ processing（話者分離・議事録）──▶ idle
エラー時は idle に戻り、それまでの録音・文字起こしは保存する
```

### 5.2 保存形式

```
~/Documents/Hanasu/Meetings/2026-11-02 1430 定例/
├── meeting.json      # メタデータ、話者名の対応表、発言の配列（話者・開始・終了・本文）、議事録の型、アクションアイテム
├── transcript.md     # [00:01:23] 話者1: …… の形式
├── minutes.md        # Gemini の議事録
├── me.m4a            # マイク（AAC 16kHz モノラル。設定で処理後に削除可）
└── others.m4a        # システム音声
```

## 6. 画面

- **メニューバー**: 「会議の記録を開始／停止」（録音中は経過時間を表示し、アイコンを赤い丸にする）、「会議ノートを開く」。
- **会議ノート ウィンドウ**: 左に会議の一覧、右に選んだ会議の「議事録」「文字起こし」タブ。録音中の会議はライブの文字起こしを表示。話者名の変更、書き出し（4.9）、議事録の型の選び直し（4.8）、Finder で開く。左下で録音する機器と議事録の型を選んでから記録を始める。
- **ショートカット**: 記録の開始／停止 `⌃⌥⌘ M`（変更可）。

## 9. 検証方法

- `say` で作った 2 人分（声の違う 2 つの音声）の会話を、「自分」側と「相手」側の音声ファイルとして後処理パイプラインに流す CLI モードを作り、文字起こし→並べ替え→議事録まで確認する。
- システム音声のタップは、`afplay` で音声を鳴らしながら数秒録音し、文字起こしできることを確認する。

## 10. 検証結果（2026-11-02）

`say` の 3 つの声（相手 2 人＋自分）で 41 秒の会議音声を作り、`--meeting-files` で後処理を確認した。

```bash
.build/debug/Hanasu --meeting-files me.wav others.wav
HANASU_DEBUG=1 .build/debug/Hanasu --meeting-files me.wav others.wav   # 語ごとの時刻も表示
```

| 項目 | 結果 |
| --- | --- |
| 文字起こし（2 チャンネル） | 41 秒の音声を 0.8〜1.2 秒で処理 |
| 自分／相手の並べ替え | 時刻順に正しく並ぶ |
| 回り込み除去（自分側に相手の声を 30% の音量で混ぜたもの） | 回り込んだ相手の発言は自分側から消えた |
| 議事録（gemini-3.8-flash、サービスアカウント） | 約 5 秒。誤認識（「オームデバイス」→ オンデバイス、「話し合う分」→ 話者分離）も文脈から補って要約した |

分かった制約:

- **回り込みがあると、自分の発言の認識そのものが崩れる。** 回り込みなしでは自分の発言が全部正しく認識されたが、回り込みありでは「オンデバイスのモデルを使う予定です。来週の金」が認識されなかった。テキストでの除去では取り戻せないので、**イヤホンの利用を前提**にする。マイク側のエコーキャンセル（Voice Processing I/O、または相手側の音声を参照信号にした自前のエコー除去）はフェーズ 2 で検討する。
- 語の時刻は、無音のあとの最初の語に無音の分まで含まれることがある（例: 「は」が 5.70〜6.78 秒）。重なりの判定は語の終わり寄り 0.4 秒だけで行うようにした。
- システム音声のタップ（Core Audio Process Tap）は、権限ダイアログ（システムオーディオ録音）を伴うため、実際の会議での確認が必要。

### 10.1 話者分離（FluidAudio 組み込み後）

| 項目 | 結果 |
| --- | --- |
| 初回のモデル準備（ダウンロード＋コンパイル） | 49.5 秒（2 回目以降 0.2〜0.8 秒） |
| 話者分離の処理時間 | 41 秒の音声で 1.0〜2.2 秒 |
| 精度 | 相手側の 2 人（Kyoko・Eddy の声）を正しく 2 人に分け、6 発言すべての話者が正しかった |
| 議事録 | 話者1・話者2・自分の発言を区別してまとめ、「話者2 は佐藤さんと呼ばれている可能性がある」と推定した |

最初は「了解です」の「了解」だけが前の話者に付いた。話者分離が 2 人目の話し始めを約 1.4 秒遅れて検出し（実際は 35.1 秒ごろ、検出は 36.50 秒）、
すき間にある語をいちばん近い区間（前の話者）に割り当てていたため。4.5 の 1 の規則（間があいて始まる語は次の話者）に変えて解消した。

### 10.2 実機で録音されなかった問題（2026-11-02）

Bluetooth イヤホン（LinkBuds Clip）を使った実際の会議で、何も文字起こしされなかった。

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 相手側の音声が 3 分の 1 の長さ（42 秒 → 13.3 秒）の、認識できない音になった | タップが報告する形式（`kAudioTapPropertyFormat`、48kHz）をそのまま使っていたが、集約デバイスの時計は主デバイスの Bluetooth イヤホン（マイク使用中は 16kHz）に合うため、実際は 16kHz のデータが届いていた | 集約デバイスの入力の実際の形式（`kAudioDevicePropertyStreamFormat`）を使う。録音中にサンプリングレートが変わったら読み直す |
| 自分側が完全な無音（ピーク 0）になった | タップを作ると Bluetooth イヤホンの接続モードが切り替わり、マイクの経路が変わったまま無音を受け取り続けた | `AVAudioEngineConfigurationChange` を受けてマイクを作り直す。入力の形式が変わったら変換器も作り直す |

| 上の修正後も、Teams で相手の音声が 3 分の 1 の長さ（58.8 秒 → 19.5 秒）になった | 集約デバイスの入力形式（`kAudioDevicePropertyStreamFormat`）も 48kHz と返るが、実際に届くのは毎秒約 16,000 サンプル（主デバイスの Bluetooth イヤホンの時計）だった | 「Mac 全体の音」では主デバイスを内蔵スピーカーにする。さらに IOProc で届くフレーム数と経過時間から実際のレートを測り、形式と 10% 以上違えば測った値に合わせる |
| 録音ボタンでクラッシュした（修正版で発生） | マイクの形式を読むために一時的に作った `AVAudioEngine` が、`inputNode` に触る前に解放されていた（ノードはエンジンを保持しない） | エンジンを変数に持ち、そのまま録音に使う |
| マイクを指定しても形式が既定の機器のまま | 機器を切り替えても `inputNode.outputFormat` は切り替え前の機器の形式のまま | `inputNode.inputFormat`（機器側の実際の形式）でタップを付ける |

あわせて次を追加した。

- 設定「会議」→「録音するスピーカー」（初期値は Mac 全体の音。特定の出力機器だけをタップすることもできる）と「録音するマイク」
- 記録中の画面に「自分」「相手」の音量メーター。始めてから 10 秒たっても一度も音が入らないチャンネルは警告を出す
- `Hanasu --list-audio-devices` で機器の一覧（UID・サンプリングレート）と、会議の記録と同じ方法で作ったマイクの形式を表示
- 起動時に、アプリの終了などで「記録中」「処理中」のまま残った会議を「失敗」にする

### 10.3 議事録の型と書き出し（2026-11-03）

架空の文字起こし（商談・1on1。実際の会議データは使っていない）で確認した。

```bash
.build/debug/Hanasu --minutes-from-transcript sales.txt --template sales --date "2026-11-03 14:00" --save-json sales.json
.build/debug/Hanasu --minutes-from-transcript 1on1.txt --template oneOnOne
.build/debug/Hanasu --minutes-from-transcript sales.txt --custom-prompt "「## 一言まとめ」と「## 宿題」だけで"
.build/debug/Hanasu --export-minutes sales.json            # Gemini を呼ばずに書き出しだけ
.build/debug/Hanasu --render-minutes-ui out/ --meeting-json sales.json   # 画面を PNG に
.build/debug/Hanasu --meeting-files me.wav others.wav --template regular  # 録音からの後処理でも型を指定できる
```

文字起こしは 1 行 1 発言（`[00:12] 話者: 発言` か `話者: 発言`）。`自分`・`話者1`・`同席者1`・`相手` は会議の話者キーに直す。

| 項目 | 結果（gemini-3.8-flash） |
| --- | --- |
| 商談（13 発言） | 8.6 秒。顧客の課題・提案内容・反応・懸念・予算/時期/決裁の見出しで出力。「今週の金曜まで」を 2026-11-06（金）に直し、担当「自分」・「話者1」を正しく付けた |
| 1on1（10 発言） | 10.2 秒。近況・相談・フィードバック・キャリア・合意の見出しで出力。「明日」→ 11/4、「月末まで」→ 11/30 |
| カスタム | 4.8 秒。指定した 2 つの見出しのあとに、アクションアイテムと話者のメモが付いた |
| 応答の読み取り | `<action_items>` をコードブロックで囲んだ応答、日付でない `due`（「来週」→ 期限の言い方へ）、空の `task`（除く）、壊れた JSON（「読み取れませんでした」と表示）を確認 |
