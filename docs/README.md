## 2. 振る舞いの 3 つの区分

| 区分 | 何か | ID | 変えるときの扱い |
| --- | --- | --- | --- |
| 要件 | ユーザーが求めた（または合意した）振る舞い | `REQ-<領域>-<番号>`（例: REQ-DIC-003） | **ユーザーの合意が要る。** 仕様書を先に直す |
| 設計判断 | 実装した人（エージェントを含む）が、要件を満たすために決めた振る舞い。理由が記録されている | `DEC-<領域>-<番号>`（例: DEC-DIC-013） | 理由を見直したうえで変えてよい。仕様書も直す |
| 暗黙の振る舞い | どちらのタグも付いていないコードの振る舞い | なし | 変える前に、要件か設計判断に格上げして書くか、暗黙のままでよいと判断する |

- 要件は「何をするか」（外から見える振る舞い）。設計判断は「どうやるか」と、要件が決めていない細部（既定値・区切り方・タイムアウト・プリセットの中身など）。
- 迷ったら設計判断にする。ユーザーの依頼・合意（日付と要旨、または PR 番号）を出典として書けるものだけを要件にする。
- 文書とコードが食い違っていて、要件を書き換えないと合わないものは、勝手に要件を変えず、その要件に「食い違い（ユーザーの確認待ち）」を書く。

## 3. ID の付け方

- 形: `REQ-<領域>-<3 桁>`、`DEC-<領域>-<3 桁>`、計画は `FUT-<3 桁>`。
- 領域: `DIC`（音声入力）、`MTG`（会議の記録）、`COM`（設定・認証・共通）、`REL`（配布・リリース）。足すときは、この表と `scripts/check-spec.py` の `DOMAINS` と spec のファイルを足す。
- 番号は、機能のまとまりごとに 10 刻みで区切りを空けてある（例: DIC の 020 番台はアプリ別の文体、050 番台は選択を声で編集）。続きの番号を使い、**使い回さない**。
- Windows 版にも同じ ID を使う。各項目の「対象」に `Mac` / `Windows` を書く。

## 4. spec の書き方

1 項目 = 1 つの見出し `### <ID> <短い名前>` と、その下の箇条書き。`scripts/check-spec.py` がこの形を読む。

要件（REQ）に書くこと:

```markdown
### REQ-DIC-003 認識結果を Gemini で自然な日本語に整える
- 内容: 何をするか
- 受け入れ条件: 外から観察できる振る舞い（入れ子の箇条書きでもよい）
- 出典: ユーザーの依頼の日付と要旨、または PR 番号
- 対象: Mac / Windows
- 実装の場所: 型・関数の名前
- 確かめ方: CLI のコマンドやテスト。なければ「実機で確かめる」
```

設計判断（DEC）に書くこと:

```markdown
### DEC-DIC-013 入力はクリップボードと ⌘V で行い、元のクリップボードを戻す
- 決めたこと: …
- 理由: …
- 決めた場面: PR 番号かコミット
- 関係する要件: REQ-DIC-004
- 対象: Mac
- 実装の場所: 型・関数の名前（任意）
```

必要なときだけ書くもの:

- `- 食い違い（ユーザーの確認待ち）: …` 要件と実装が合わず、ユーザーの判断を待っているもの。
- `- コードのタグ: 不要（理由）` 要件のうち、コードに決めている場所がないもの（「対象外」の要件や、全体の性質の非機能要件）。これがない要件は、コードのタグが 1 つもないとエラーになる。
- `- 状態: 廃止（日付・理由・PR）` やめた要件・設計判断。項目は消さずに、spec のファイルの最後の「## 廃止」の節へ移し、コードのタグは外す。ID は使い回さない。

## 5. コードのタグ

その振る舞いを決めているところ（関数や型の宣言の直前など）に、コメントで書く。

```swift
// 要件: REQ-DIC-004
// 設計判断: DEC-DIC-013, DEC-DIC-014
enum TextInserter {
```

- `// 要件: …` には REQ だけ、`// 設計判断: …` には DEC だけを書く。1 行に複数並べてよい（`,` か `、` で区切る）。
- YAML・シェルでは `# 要件: …`。
- 要件の「確かめ方」に挙げた CLI の入口やテストには、`// 確かめ方: REQ-…` を書く（どの要件を確かめるものか）。
- ドキュメントコメント（`///`）がある宣言では、`///` の前に置く。
- すべての要件に、少なくとも 1 か所付ける。設計判断は、コードの場所がはっきりしているものに付ける。
- タグのないコードは「暗黙の振る舞い」。タグのないファイルが多いところほど、暗黙の振る舞いが多い（`check-spec.py` が一覧を出す）。

## 6. 変更の手順

### 新しい機能を作るとき
1. 依頼から要件を [spec/](spec/) に書く（出典に依頼の日付と要旨）。[roadmap.md](roadmap.md) の項目を実装するなら、その中身を spec に移し、roadmap には「→ REQ-…」だけを残す。
2. 実装しながら決めたことを、設計判断として spec に書く（理由と PR 番号）。
3. コードにタグを付ける。
4. 実装の説明を [design/](design/) に、検証の結果を日付つきで [verification/](verification/) に書く。
5. `python3 scripts/check-spec.py` を通す。

### 既存の振る舞いを変えるとき
1. 変える場所のコードのタグと、spec の項目を見る。
2. 区分ごとに:
   - **要件**: ユーザーの合意を取ってから、spec の要件を先に直す（出典に合意の日付と要旨を足す）。
   - **設計判断**: 理由を読み、その理由がもう当てはまらないことを確かめてから変える。spec の「決めたこと」「理由」「決めた場面」を直す。
   - **暗黙の振る舞い**（タグがない）: 変える前に、その振る舞いを要件か設計判断として spec に書いて（格上げして）タグを付けるか、暗黙のままでよい（記録するほどの振る舞いではない）と判断する。要件に当たりそうなら、ユーザーに確かめる。
3. design・README の説明を直す（README の訳も。8 章）。検証の記録（verification）は書き換えず、新しい結果を足す。
4. `python3 scripts/check-spec.py` を通す。

### 機能をなくすとき
1. 要件ならユーザーの合意を取る。
2. spec の項目は消さず、同じファイルの「## 廃止」の節へ移し、`- 状態: 廃止（日付・理由・PR）` を書く。ID は使い回さない。
3. コードのタグを外す（タグが廃止の ID を指しているとエラーになる）。

### PR を作るとき
- [.github/pull_request_template.md](../.github/pull_request_template.md) の項目（触った要件・設計判断の ID、Spec-Impact、新しい要件の合意、roadmap から移したもの）を書く。
- spec を直さなくてよい変更（タグのあるコードの、振る舞いを変えない整理など）は、PR の本文かコミットメッセージに `Spec-Impact: なし（理由）` と書く。

### 計画を書くとき
- [roadmap.md](roadmap.md) に `FUT-<番号>` で書く。spec と design には「まだ作っていない」ことを書かない（design に書くときは「…はしない（FUT-…）」のように、いまの振る舞いとして書く）。
- 大きな計画は [plans/](plans/) に書き、roadmap から参照する。

## 7. 確かめる仕組み

`python3 scripts/check-spec.py`（python3 の標準ライブラリだけ）。PR ごとに `.github/workflows/spec.yml` で動く（PR では `--diff origin/main` も動かす）。

エラーにする（終了コード 1）もの:

- spec の ID が重複している、形が違う、必須の項目がない、「対象」に Mac / Windows がない
- 「関係する要件」が、ない要件を指している
- コードのタグが、ない ID・廃止した ID を指している。`要件:` に DEC を書くなど、区分が合わない
- 要件に、コードのタグが 1 つもない（「コードのタグ: 不要」がないとき）
- 文書の中の ID（REQ / DEC / FUT）が、どこにも定義されていない
- 文書の中の相対リンクの先がない
- 文書が名前を挙げた `Sources/…`・`windows/…` のファイルがない
- 廃止の項目が「## 廃止」の節にない（または逆）
- `--diff <base>`: 要件・設計判断のタグのあるコード（タグの付いた宣言の中）を変えたのに `docs/spec/` を直していない（`Spec-Impact: なし（理由）` があれば通す）

報告だけするもの:

- 設計判断のうち、タグのないもの
- ファイルごとのタグの数と、タグのないファイルの一覧（＝暗黙の振る舞いが多い場所の目安）
- 「食い違い（ユーザーの確認待ち）」の一覧
- 対象が Windows だけの要件で、タグがまだないもの（`windows/` のタグ付けが済むまで。FUT-002）
- 確かめ方が実機だけの要件と、確かめ方の CLI・テストに `// 確かめ方:` の ID がない要件
- `--diff <base>` の警告: タグを消したのに spec に残っている ID、spec から消した（廃止に移していない）項目、タグが 1 つもない新しいソースファイル

`--diff` の「触った」は近似: 変わった行から上へ、インデントの浅い行（宣言の書き出し）をたどり、その直前のタグを拾う。

## 8. 多言語

- 対応言語は README と同じ 17 言語（en, ja, zh-CN, zh-TW, ko, es, fr, de, it, pt-BR, ru, tr, vi, id, pl, ar, hi）。どれでもなければ英語（REQ-COM-061）。
- **UI の文字列と AI へのプロンプトを足す・変えるときは、同じ変更の中で 17 言語すべての訳を入れる**（REQ-COM-062）。訳の質は「その言語の話し手が自然に読める・話せる」ことで、直訳にしない（DEC-COM-162）。
- AI へのプロンプトは `Sources/Hanasu/Resources/Prompts/<言語>.json` に置き、Mac と Windows で同じファイルを読む（DEC-COM-160）。どの言語のプロンプトを使うかは、文字起こしの言語で決まる（DEC-COM-161）。コードには文面を書かず、キー（`Prompts.text("…")`）で読む。
- 手順（キーの足し方・訳の入れ方・漏れの確かめ方）は [.claude/skills/i18n/SKILL.md](../.claude/skills/i18n/SKILL.md)。訳は [.claude/agents/i18n.md](../.claude/agents/i18n.md) のエージェントに任せる。
- `python3 scripts/check-i18n.py` が、キーの漏れ・埋める場所（`${…}`）やタグの食い違いを見つける（エラーなら終了コード 1。PR ごとに `.github/workflows/spec.yml` で動く）。
- 表示の言語はシステムの言語で決まる（REQ-COM-060）。Mac の UI の文字列は `tr("日本語の原文")` で書き、訳は `Sources/Hanasu/Resources/Localizable.xcstrings` に入れる（DEC-COM-165）。
- 開発用の CLI の出力とログは訳さない。
- README も 17 言語。英語（`README.md`）と日本語（`README.ja.md`）を正とし、ほかの 15 言語（`README.<言語>.md`）は `README.md` から訳す（冒頭に「英語版と食い違ったら英語版が新しい」と書いてある）。**`README.md` を直すときは、同じ変更の中で 15 の訳にも同じ変更を入れる**（訳は [.claude/agents/i18n.md](../.claude/agents/i18n.md) のエージェントに任せてよい）。表の行・`<kbd>`・リンクの数が `README.md` とそろっていることを確かめる。言語を足すときは、すべての README の言語の切り替え（18 行目あたり）に足す。
- Windows の UI の文字列は `Properties/Strings.resx`（英語）と言語ごとの `Strings.<カルチャ>.resx` に置き、起動のときに Windows の表示の言語から 17 言語のどれかに決める（REQ-COM-060、DEC-COM-167）。訳の出し入れと漏れの確かめは `scripts/i18n-resx.py`。
